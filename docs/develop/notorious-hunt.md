# 恶名狩猎周常计划

M5 在迷失之地离线开发完成后，继续迁移不消耗电量的恶名狩猎周常。它与体力计划中的深度追猎分别配置、分别记账。已实现按账号及应用组保存计划、旧配置转换和只读估算，并接通副本入口、免费余量、等级及选队的内部流程；出战、完整挑战、领奖和成功登记继续开发。

依据为参考仓的 `notorious_hunt_config.py`、`notorious_hunt_app.py`、`notorious_hunt_run_record.py`、公共 `ChargePlanItem`、快捷手册目录及 `notorious_hunt.yml`。复用体力目录中的恶名狩猎完整名称、六档等级、二十个预备编队与三项鸣徽。计划用独立 UUID 区分，同一副本可以有多条计划；旧次数仅作计划基线，不导入为新版通关或剩余奖励证明。

开始星期使用账号区服的游戏日，周一为 1、周日为 7。估算只采用人工填写的 0..3 次剩余周奖励；留空保持未知，不能从旧记录或计划次数推测。未到开始日、没有有效计划、本轮完成、余量耗尽及余量未知分别显示。普通计划按保存顺序消耗估算余量，循环仅在所有非零目标均完成时扣除完整轮数，再继续分配，最多生成三次挑战。预备编队采用该槽位保存的脚本，保持当前队伍时采用计划脚本。代理人方案培养仍需导航和实际达成读取，估算遇到它即停止预分配后续奖励，不假定培养目标存在或已完成。

估算返回有效基线及冻结的脚本名称，不写回次数、配置或运行历史。保存、旧配置导入、复制及备份恢复共同校验分类、UUID 唯一性、目标、基线、等级、编队、鸣徽与脚本。旧组目录优先于账号级配置；旧“挑战”或“作战”页签统一转换成当前“训练”，旧临时跳过标记不保留。没有 UUID 的旧计划按内容及位置确定性生成，重复副本也不会合并。未知旧计划字段、错误类型及不属于恶名狩猎的分类拒绝转换。

桌面通过统一设置命令保存，估算复验账号、组及配置修订；编辑、切页和连接变化会使旧结果失效。导入和恢复预览显示完整设置，正式可用标记保持不变。副本入口、免费奖励余量及等级选队见下文；代理人培养、列表查找、出战、战斗、领奖和周记录继续接入，全部实际游戏验收保留。

协议为 v56、导入预览为 v22，既有执行资源不变。六份参考来源及 SHA-256 保存在 `resources/notorious-hunt/source-lock.json`，副本目录继续使用体力计划的唯一来源，不另外维护一份。

```powershell
cargo test --locked --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/lost-void --test notorious_hunt -- --test-threads=1
target/lost-void/debug/zzz-engine.exe --data <数据目录绝对路径> notorious-hunt-preview --instance-id 1 --group-id one_dragon --rewards-left 3
```

CLI 不初始化 SDK，省略 `--rewards-left` 表示未知。数据目录不存在时读取默认空计划，不创建目录；无效余量拒绝返回估算。

## 副本入口与免费余量

内部入口复用同次快捷手册传送及既有深度追猎只读资源。普通副本按完整目录名称及登记别名配对；传送到了其他已知详情时，先保存返回列表意图，实际看到列表后才选择目标。选择或返回的投递未知、暂停均保留原意图，不重复点击。没有唯一目标时保持待验证，不推测滚动方向。代理人培养导航继续单独接入。

免费余量必须与同帧街区、完整副本标题、完整“剩余奖励次数”和下一步共同出现，单行数字仅接受 1..3；深度信息、ON / OFF、无报酬模式、费用数字或“电量消耗”与免费证明冲突时不提供可用余量。明确深度信息按参考行为只证明周常已耗尽，不形成可挑战许可。连续两张新帧的同一读数才交回；未知和暂停撤销之前的连续证明，不能使用旧记录补值。

父任务冻结传送及追猎资源，共用运行 ID、原生槽位、控制句柄和总活动预算。输入前保存独立意图，投递前重新截图核对，继续时重新读取，终态保存失败、迟到控制、超时或未释放输入均不提供回执。内部回执只说明本次目标详情和免费余量已观察，不证明等级、选队、出战或奖励成功；普通运行入口仍保持关闭。采用明确标注的组合帧验证，真实详情与次数布局继续保留实机验收。

`WeeklyHuntApproachRun` 继承父调用方持有的原生会话，不从序列化快照创建执行器。`WeeklyEntryFlow` 保存返回、选择及连续读数，`WeeklyApproachReceipt` 只在实际执行器安全交回后取得。`Observed` 表示 1..3 次免费余量已观察，`Exhausted` 表示明确耗尽，两者都不能登记通关；未知及重复目标返回 `AwaitingVerification`。旧深度追猎的消费规则和资源定义保持不变。此阶段复用传送与追猎包既有来源，不另复制模型或修改资源 schema。

```powershell
target/lost-void/debug/zzz-engine.exe weekly-hunt-inspect --mission-type 初生死路屠夫 --image <1920x1080图片路径>
cargo test --locked --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/lost-void --test weekly_hunt_entry -- --test-threads=1
```

固定图检查使用 CPU 和既有深度追猎资源，需要已安装 SDK，保持 `accepted=false`、`input_sent=false`、`completion_verified=false`。固定图中的一次观察不代替实际执行器的连续新帧及本次传送证明。

## 等级与选队准备

`WeeklyHuntPreparationRun` 从同一运行 ID 的普通传送和免费次数观察开始，接续等级准备及公共 `TeamsRun`，到达出战页后交回。它只接受普通副本；免费余量耗尽直接交回 `Exhausted`，不打开深度追猎、不恢复电量，也不写挑战次数或周成功记录。脚本名称取冻结的计划或预备编队，此阶段不加载或执行战斗脚本。

依据仍为参考 `notorious_hunt.py` 的选择难度、下一步及预备编队节点，和已登记的等级区域、出战页与公共选队规则。默认等级不修改现有选择；指定等级先读取完整名称，已是目标时直接采用，否则分别保存打开菜单和选择的意图。每次动作须有连续两张新帧的本次目标、相同免费余量及对应等级上下文，输入前再次截图复验。菜单中的目标须唯一，选择后重新读到目标等级才允许下一步；不重复点击最高等级。未知、余量变化、费用、深度模式、错误目标或未由本流程打开的菜单不能继续。

只有本次保存的“下一步”意图及实际出战页同时成立，才交给公共选队；保持当前队伍时只重新读出战页。指定编队沿用二十槽清空、按槽选择、全表复核和返回确认，冻结名称、成员及脚本设置，准备流程不改写账号配置。等级、下一步和选队已投递后暂停，仅核对后态；终态保存期间暂停后也重新读出战页，不重复选择。

首个导航输入前预检并冻结传送、深度追猎只读包、等级、模拟室选队及日常资源。默认等级也载入等级识别，以排除未关闭的外部菜单。复用同一父会话、控制句柄及剩余活动预算；保存、加载、释放和资源复验全部计时。保存失败、迟到停止、超时及未释放输入不提供 `WeeklyPreparationReceipt`。该回执只证明本次等级与选队准备，不能提供关卡消费、战斗或奖励成功。

现有执行资源 schema、协议 v56、导入预览 v22 及恢复输入版本不变。普通公开运行入口仍未开放；下一步接通出战、低等级确认、战前移动及冻结战斗，再接领奖和周记录。真实免费详情、等级菜单、操作时序及连续挑战继续保留实机验收。

```powershell
target/lost-void/debug/zzz-engine.exe weekly-hunt-preparation-inspect --mission-type 初生死路屠夫 --image <1920x1080图片路径>
cargo test --locked --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/lost-void --test weekly_hunt_preparation -- --test-threads=1
```

只读检查另接受 `--level-bundle` 指定已校验等级包，保持 `accepted=false`、`input_sent=false`、`selection_verified=false` 和 `completion_verified=false`。组合图仅用于检查识别、实际 Maa 队列和父子流程，不能替代实机画面。
