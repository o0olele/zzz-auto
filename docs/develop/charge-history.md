# 体力次数保存与启动恢复

`ConfigStore::commit_charge_run` 接收[调度器](charge-run.md)已经核实的检查点，先保存完整日志，再原子写回该账号、应用组的次数和去重回执。`ChargeRegistrar::begin_persisted` 与 `record_persisted` 接入实际挑战实例，记录自身提交产生的新配置修订；原冻结请求继续保留启动时的修订，用于复验历史，不修改战斗或计划参数。

区域巡防经 `record_patrol_persisted` 采用其私有运行实例的正常完成或实际电量不足终态；独立类别和执行 UUID 防止混用模拟室证明。成功增加一次，不足不计成功；完整结果保存失败后仍使用同一补交入口，停止期间只保存结果，不再操作游戏。体力父循环已接入区域分支，实际私有结果由内部登记接口保存后才允许下一轮；迟到控制请求和配置变化不能撤销已取得的正常消费日志。

专业挑战室经 `record_expert_persisted` 采用独立父任务的私有终态，常规费用固定 40 电量，须先确认燃竭 OFF。父循环内部采用同一日志提交路径；未知模式、未确认费用、失败及撤退不记成功，实际不足不增加次数。与区域、模拟室和合成严格区分类别，执行 UUID 去重、保存失败补交及启动恢复沿用原规则。

深度追猎经 `record_hunt_persisted` 采用独立父任务的私有终态，须核对同次完整目标、周常耗尽、深度 ON 和实际 60 电量。周常仍有 1..3 次奖励单独登记 `HuntWeeklyRewardsAvailable`，本次运行跳过该项，成功次数保持原值；冻结的电量不足跳过开关不影响此规则。整组保留 `WeeklyRewardsAvailable` 结果，不能据此写每日成功。日志继续 schema 1，旧记录按原类别及规则重放。

日志保存在固定数据目录 `runs/charge/<运行 UUID>.json`，schema 1；账号配置增加可缺省的 `charge_commits`，旧文件按空列表读取。计数和回执同处 `accounts.yml`，沿用独占锁、原子替换、原文备份及目录联接拒绝。每份日志最多 8 MiB，启动扫描最多 10000 项、64 MiB，配置最多保留最近 256 个运行回执；旧回执移出后，原启动修订也不能覆盖更新的配置。

[体力应用记录](charge-application.md)现已用同一运行身份引用该日志，在通用 RunRecord 内保存紧凑摘要。只有实际父实例正常结束、返回大世界、输入释放且次数提交完成，才提供每日成功；读取完成记录时重新核对原始日志及完整指纹。该层不改写消费事实，历史补存也不重新执行挑战，正式运行入口仍待接通。

回执绑定运行身份、账号、应用组、区服游戏日、启动修订、已确认记录数量、完整日志前缀 SHA-256 和保存修订。同一运行只能追加记录，不能更换冻结请求、撤销当前意图或改写旧结果。相同提交重试只确认已生效；旧快照、外来配置分支和同基线冲突均不能覆盖当前次数。即使保存后的循环意图已将内部次数扣减，用户次数仍只采用已确认记录的投影，不能提前写入未执行的一轮。

配置写入失败时保留日志，并冻结已取得的结果，阻止重新挑战。`retry_pending_persisted` 只补交此前核实的结果，在暂停或停止期间也不重放输入。已有输入意图的运行在配置变更后仍保留随后核实的结果，但拒绝覆盖新设置；每次继续还复验设置内容，不能只凭相同修订接受手工改动。引擎取得数据目录所有权、读取正常配置之后，在任何游戏输入和 SDK 初始化之前检查日志：同一配置分支有未提交结果时补交一次；已提交结果不再累计，旧设置分支只保留历史并记日志。仅有意图而无结果时不增加次数，也不恢复游戏输入。

损坏、改名、超量、无法复验、缺失原配置且存在备份，或多个运行争用同一基线时，拒绝自动恢复。配置备份恢复一并保留当时的次数与回执；主动恢复到更早次数后，旧日志不能把恢复操作自动撤销。修改其他配置产生的新修订也不能被后来的旧结果覆盖。

本项升级协议至 v47，导入预览仍为 v19，既有执行资源的定义和兼容范围保留。日志只提供已核实结果的恢复；完整体力工作线程、应用运行历史页、传送至挑战的自动循环及其他副本仍在当前目标内继续开发，不因次数存储接通而登记应用每日成功。新字段的配置应由配套的新引擎读取。
