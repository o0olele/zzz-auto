# 恶名狩猎周常计划

M5 在迷失之地离线开发完成后，继续迁移不消耗电量的恶名狩猎周常。它与体力计划中的深度追猎分别配置、分别记账。已实现按账号及应用组保存计划、旧配置转换和只读估算，并接通普通副本入口、免费余量、等级选队、出战、战前移动、冻结战斗、单战结算和周记录。计划调度与逐战登记已实现，完整应用循环、代理人培养及周奖励领取继续开发。

依据为参考仓的 `notorious_hunt_config.py`、`notorious_hunt_app.py`、`notorious_hunt_run_record.py`、公共 `ChargePlanItem`、快捷手册目录及 `notorious_hunt.yml`。复用体力目录中的恶名狩猎完整名称、六档等级、二十个预备编队与三项鸣徽。计划用独立 UUID 区分，同一副本可以有多条计划；旧次数仅作计划基线，不导入为新版通关或剩余奖励证明。

开始星期使用账号区服的游戏日，周一为 1、周日为 7。估算只采用人工填写的 0..3 次剩余周奖励；留空保持未知，不能从旧记录或计划次数推测。未到开始日、没有有效计划、本轮完成、余量耗尽及余量未知分别显示。普通计划按保存顺序消耗估算余量，循环仅在所有非零目标均完成时扣除完整轮数，再继续分配，最多生成三次挑战。预备编队采用该槽位保存的脚本，保持当前队伍时采用计划脚本。代理人方案培养仍需导航和实际达成读取，估算遇到它即停止预分配后续奖励，不假定培养目标存在或已完成。

估算返回有效基线及冻结的脚本名称，不写回次数、配置或运行历史。保存、旧配置导入、复制及备份恢复共同校验分类、UUID 唯一性、目标、基线、等级、编队、鸣徽与脚本。旧组目录优先于账号级配置；旧“挑战”或“作战”页签统一转换成当前“训练”，旧临时跳过标记不保留。没有 UUID 的旧计划按内容及位置确定性生成，重复副本也不会合并。未知旧计划字段、错误类型及不属于恶名狩猎的分类拒绝转换。

桌面通过统一设置命令保存，估算复验账号、组及配置修订；编辑、切页和连接变化会使旧结果失效。“读取本周记录”显示当前账号所在游戏周的已登记成功次数及最近观察到的免费余量，跨周显示未知。导入和恢复预览显示完整设置，正式可用标记保持不变。副本入口、列表查找、免费奖励余量、等级选队、普通单战、撤退收尾与周记录见下文；代理人培养、超时退出、完整循环和周奖励领取继续接入，全部实际游戏验收保留。

协议为 v57、导入预览为 v22，既有执行资源不变。六份参考来源及 SHA-256 保存在 `resources/notorious-hunt/source-lock.json`，副本目录继续使用体力计划的唯一来源，不另外维护一份。

```powershell
cargo test --locked --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/lost-void --test notorious_hunt -- --test-threads=1
target/lost-void/debug/zzz-engine.exe --data <数据目录绝对路径> notorious-hunt-preview --instance-id 1 --group-id one_dragon --rewards-left 3
```

CLI 不初始化 SDK，省略 `--rewards-left` 表示未知。数据目录不存在时读取默认空计划，不创建目录；无效余量拒绝返回估算。

## 副本入口与免费余量

内部入口复用同次快捷手册传送及既有深度追猎只读资源。普通副本按完整目录名称及登记别名配对；传送到了其他已知详情时，先保存返回列表意图，实际看到列表后才选择目标。选择或返回的投递未知、暂停均保留原意图，不重复点击。没有唯一目标时按下述目录证明查找，无法确定方向时保持待验证。代理人培养由下述专用父流程交接本次实际导航结果。

免费余量必须与同帧街区、完整副本标题、完整“剩余奖励次数”和下一步共同出现，单行数字仅接受 1..3；深度信息、ON / OFF、无报酬模式、费用数字或“电量消耗”与免费证明冲突时不提供可用余量。明确深度信息按参考行为只证明周常已耗尽，不形成可挑战许可。连续两张新帧的同一读数才交回；未知和暂停撤销之前的连续证明，不能使用旧记录补值。

父任务冻结传送及追猎资源，共用运行 ID、原生槽位、控制句柄和总活动预算。输入前保存独立意图，投递前重新截图核对，继续时重新读取，终态保存失败、迟到控制、超时或未释放输入均不提供回执。内部回执只说明本次目标详情和免费余量已观察，不证明等级、选队、出战或奖励成功；普通运行入口仍保持关闭。采用明确标注的组合帧验证，真实详情与次数布局继续保留实机验收。

`WeeklyHuntApproachRun` 继承父调用方持有的原生会话，不从序列化快照创建执行器。`WeeklyEntryFlow` 保存返回、选择及连续读数，`WeeklyApproachReceipt` 只在实际执行器安全交回后取得。`Observed` 表示 1..3 次免费余量已观察，`Exhausted` 表示明确耗尽，两者都不能登记通关；未知及重复目标返回 `AwaitingVerification`。旧深度追猎的消费规则和资源定义保持不变。此阶段复用传送与追猎包既有来源，不另复制模型或修改资源 schema。

```powershell
target/lost-void/debug/zzz-engine.exe weekly-hunt-inspect --mission-type 初生死路屠夫 --image <1920x1080图片路径>
cargo test --locked --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/lost-void --test weekly_hunt_entry -- --test-threads=1
```

固定图检查使用 CPU 和既有深度追猎资源，需要已安装 SDK，保持 `accepted=false`、`input_sent=false`、`completion_verified=false`。固定图中的一次观察不代替实际执行器的连续新帧及本次传送证明。

## 列表查找

`WeeklyListSearch` 使用同一份快捷手册目录和列表标题区域。目标未出现时，连续两帧须读到相同的一组已知副本，且这些副本在目录中全部位于目标同一侧，才决定向左或向右拖动 500 像素。输入前再次截图核对整组名称；重复、混合方向、未知或空读数不提供拖动许可。

每次拖动先保存意图，原生适配器从固定列表中心按下、移动并释放。只要起点已经投递，部分拖动、投递不明及暂停都不重发原页面动作；新页面仍须两次连续确认。最多十二次拖动，页面不变、回到旧页或方向不明连续三次即交回待验证。找到唯一目标后沿用选择和免费余量复核，不从列表位置推断奖励次数。

## 等级与选队准备

`WeeklyHuntPreparationRun` 从同一运行 ID 的普通传送和免费次数观察开始，接续等级准备及公共 `TeamsRun`，到达出战页后交回。它只接受普通副本；免费余量耗尽直接交回 `Exhausted`，不打开深度追猎、不恢复电量，也不写挑战次数或周成功记录。脚本名称取冻结的计划或预备编队，此阶段不加载或执行战斗脚本。

依据仍为参考 `notorious_hunt.py` 的选择难度、下一步及预备编队节点，和已登记的等级区域、出战页与公共选队规则。默认等级不修改现有选择；指定等级先读取完整名称，已是目标时直接采用，否则分别保存打开菜单和选择的意图。每次动作须有连续两张新帧的本次目标、相同免费余量及对应等级上下文，输入前再次截图复验。菜单中的目标须唯一，选择后重新读到目标等级才允许下一步；不重复点击最高等级。未知、余量变化、费用、深度模式、错误目标或未由本流程打开的菜单不能继续。

只有本次保存的“下一步”意图及实际出战页同时成立，才交给公共选队；保持当前队伍时只重新读出战页。指定编队沿用二十槽清空、按槽选择、全表复核和返回确认，冻结名称、成员及脚本设置，准备流程不改写账号配置。等级、下一步和选队已投递后暂停，仅核对后态；终态保存期间暂停后也重新读出战页，不重复选择。

首个导航输入前预检并冻结传送、深度追猎只读包、等级、模拟室选队及日常资源。默认等级也载入等级识别，以排除未关闭的外部菜单。复用同一父会话、控制句柄及剩余活动预算；保存、加载、释放和资源复验全部计时。保存失败、迟到停止、超时及未释放输入不提供 `WeeklyPreparationReceipt`。该回执只证明本次等级与选队准备，不能提供关卡消费、战斗或奖励成功。

现有执行资源 schema、协议 v56、导入预览 v22 及恢复输入版本不变。普通公开运行入口仍未开放；后续出战、低等级确认、战前移动及冻结战斗见下文。真实免费详情、等级菜单、操作时序及连续挑战继续保留实机验收。

```powershell
target/lost-void/debug/zzz-engine.exe weekly-hunt-preparation-inspect --mission-type 初生死路屠夫 --image <1920x1080图片路径>
cargo test --locked --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/lost-void --test weekly_hunt_preparation -- --test-threads=1
```

只读检查另接受 `--level-bundle` 指定已校验等级包，保持 `accepted=false`、`input_sent=false`、`selection_verified=false` 和 `completion_verified=false`。组合图仅用于检查识别、实际 Maa 队列和父子流程，不能替代实机画面。

## 普通单战与免费余量结算

`WeeklyHuntChallengeRun` 在第一个导航输入前预检全部七类资源并持有编译后的战斗脚本，从普通准备流程接续公共出战、低等级确认、鸣徽与战前移动、子战斗及结算。周常使用独立 `WeeklyDeployRequest`，要求同次免费准备和一致的选队脚本；本次出战意图后才接受普通攻击或交互按钮作为进入证明。交互入口仅由周常前置显式启用，模拟室的原识别条件保持。共用出战转入子战斗时也保留冻结脚本修订，运行中源脚本变化不替换内存脚本。

同一父任务管理窗口、原生槽位、界面前台 CPU 与冻结战斗输入 / 设备的交接、控制句柄和累计活动预算。战前移动另外保留累计 120 秒上限。暂停后重新读取，出战、低等级确认、鸣徽、完成和奖励确认的已投递动作不重复；终态保存期间暂停撤销余量完成证明，继续时再次读取两帧返回详情。保存失败、未释放输入、停止和累计超时均不提供成功证明。

`WeeklySettlementFlow` 只接受正常完成的本次战斗。完成按钮、可选战斗奖励弹窗和确认各自留存意图；连续两张新帧读取到同一副本，且免费余量相对准备时恰好减少一次，才形成单战证明。最后一次免费奖励采用明确的耗尽详情，不能从数字缺失推断零。错误副本、未减少、额外减少、外部结算或未确认奖励均不能计为本次成功。

证明绑定运行 UUID、独立执行 UUID、冻结计划以及实际前后余量，由下述登记器写回计划次数及周记录。本次战斗明确撤退或移动 / 战斗达到自身时限后接入下述失败收尾；培养由专用父流程接入。公开入口、完整应用循环和周奖励领取继续接入。沿用既有资源 schema 与导入预览 v22，不开放正式可用标记。

```powershell
cargo test --locked --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/lost-void --test weekly_hunt_challenge -- --test-threads=1
```

## 本次战斗失败收尾

`WeeklyRecoveryFlow` 仅接受本次子战斗连续确认的撤退结果和准备时的 1..3 次免费余量。先保存撤退意图，在实际失败结果页保存退出意图，各动作输入前重新截图核对唯一控件。已有退出页、完成 / 奖励页、撤退与退出同时出现的冲突画面均不能越步骤输入，也不使用倒带。

退出后连续两张新帧须为原副本，且免费次数与战前完全一致，才交回 `RecoveredFailure`。父流程共用原窗口、控制器、累计预算及资源校验，先释放输入再交接；暂停保留已经投递的动作，终态期间暂停则重新核对返回详情。保存失败、余量变化、错副本、停止、超时或释放失败都不能提供已收尾结果。

登记器仅从这个活挑战执行器取得 `ChallengeFailed`，将该计划标为本轮跳过，不增加挑战成功次数，也不会原地重新挑战。完整应用循环负责后续计划和周奖励领取。

`WeeklyTimeoutRun` 只在本次出战后的移动累计达到 120 秒，或冻结战斗达到自己的时限且应用仍有剩余预算时启动。共享战斗用独立错误类型区分自身时限、父预算和交接超时；保存失败保留原错误，不能触发退出恢复。先释放所有战斗输入，再以菜单按钮模板、战况 / 设置标题和返回标记确认页面，依次打开菜单、退出战斗、确认退出。菜单模板在完整图标范围匹配，点击仍用原内部坐标；退出文字使用原图 OCR，单独核对白色启用状态，避免色彩过滤损失文字。

各动作须连续新帧及投递前复核，暂停和投递不明不重发。未知、已有外部确认框、禁用按钮、用途不符或已停止均不能推进。只有本次确认退出后的结果页，或实际出现的撤退结果，才交接上述退出和免费次数核对；确认原余量未变后仅登记本轮跳过。总预算用尽、保存失败或释放失败直接停止，不另加收尾时长。

## 代理人培养

`WeeklyAgentRun` 在第一次输入前冻结培养导航、目标观察、战斗及结算资源和脚本。本次 `AgentTransportRun` 的实际回执解析具体副本，沿用同一控制句柄、原生槽位和剩余预算进入周常准备；不会重新打开手册或手动选择目标。导航未找到明确目标时登记原培养计划本轮跳过，不消费免费次数。

完成页在同帧读取完整“已达成”或“未达成”，与本次完成意图绑定，投递前重新核对；目标变化撤销点击。只有实际成功结算且免费余量恰好减一，才给原培养计划增加一次。已达成则跳过本轮剩余培养；未达成继续计划；含糊读数保留已证明的单次成功并转待验证。暂停、保存失败及未释放输入均不提供可登记结果，重复登记保持幂等。

## 计划调度与周记录

`WeeklySchedule` 冻结账号、组、区服游戏日、配置修订、计划顺序和编队。每次成功都要求独立执行身份、实际免费余量恰好减一，且与同次运行的前一结果连续；同一结果重复提交不增加次数。整轮扣减仅影响有确认结果的投影，尚未完成的下一战意图不会改写配置基线。已跳过的代理人不阻止下一轮，普通失败仍阻止整轮扣减。普通挑战、撤退 / 超时收尾及培养结果均从本次活执行器提交，完整应用循环继续接入。

`WeeklyHuntRegistrar` 只接受同一活执行器、运行身份、控制句柄、计划及编队的终态。正常结算才增加计划次数；明确耗尽仅保存零余量，待验证不增加成功次数。保存失败保留待补交结果并禁止下一战；已经取得并释放输入的结果可在迟到暂停或停止期间补交，不再调用游戏执行器。磁盘检查点不能恢复输入。

数据先写 `runs/notorious-hunt/<run-id>.json`，再在同一个配置锁内原子更新计划次数和去重回执。启动前一起核验体力与周常历史，补交同一配置分支的已确认结果；配置改变时保留历史，不覆盖当前设置。多个应用争用同一基线、历史改写或损坏均拒绝自动选择。备份恢复保留所选备份的次数与回执，旧日志不能撤销用户恢复。

周观察按账号、区服和游戏周归属，组内计划次数仍独立。记录不会在周一推定新的三次余量，也不为后续挑战提供输入许可；执行时仍从新帧读取。当前协议提供只读 `get_notorious_hunt_record`，桌面及以下 CLI 均可查看，不初始化游戏 SDK：

```powershell
target/lost-void/debug/zzz-engine.exe --data <数据目录绝对路径> notorious-hunt-record --instance-id 1
cargo test --locked --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/lost-void --test weekly_hunt_run --test weekly_hunt_history -- --test-threads=1
```
