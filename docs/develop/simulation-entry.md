# 模拟室详情推进与选队交接

内部 `EntryRun` 衔接已完成的卡片 / 电量准备、详情页“下一步”、实际出战页、已有选队执行器和 `DeploymentRun`。父任务提供已验证的冻结关卡、完整准备结果和输入释放证明；保持同一运行 ID、控制句柄、前台控制器及剩余活动预算。首次下一步输入前已经完成战斗脚本编译，选队后一次性移交同一份 `PreparedDeployment`，后续脚本导入不改变本次指令。

流程依据为参考仓 `CombatSimulation.click_next`、`combat_simulation.yml` 和 `docs/game/screens/实战模拟室.md`。复用原 schema 1 模拟室识别资源和既有选队资源，没有新增推测区域或模板。足额详情推进与不足电量打开恢复弹窗共用同帧输入实现，各自检查冻结条件。

`EntryRequest` 冻结完整计划、关卡回执、实际准备结果、二十槽位编队及预算。关卡必须明确 `selection_verified=true`；准备结果只提供数量 / 电量，仍要求 `selection_verified=false`，并且为足额 `Ready`。当前 `MissionRun` 固定返回未验证回执，因此实际生产链在此继续拦截，没有增加手动绕过开关、桌面或 CLI 带输入入口，体力应用仍未开放执行。

详情页必须同时读到挑战等级、下一步和实际电量。所需电量须与准备结果一致；当前电量允许自然增加，减少或数量变化要求重新准备。输入前保存意图，再重新截图、检查弹窗与电量，保持 1500ms 帧龄限制。明确未投递才能重新读帧后重试；已投递或无法确定是否投递时，暂停继续只等待实际出战页，不重复下一步。没有本次推进意图的已有出战页、卡片页、奖励、结算或异常弹窗均不能提供到达证明。

只有推进后的新帧同时提供出战与预备编队上下文，才交接 `TeamsRun`。保持当前队伍时不打开列表，指定队伍时沿用清除、选择和全表复核。选队终态、保存结果及输入释放全部完成，且没有暂停 / 停止请求或超时，才能通过消费 `self` 的 `into_deployment` 生成 `DeploymentRun`。转换本身不发送出战输入，也不写计划次数、每日成功或应用完成。子战斗的键鼠 / 手柄切换仍由完整父任务按已有会话接口处理。

所有读帧、资源检查、保存、等待、输入和收尾时间计入同一父预算；暂停时间不累计，继续保留本地累计时间及剩余父预算。停止优先于继续；子流程及父流程终态保存期间的控制请求、保存失败和输入释放失败均阻止正常交回。
