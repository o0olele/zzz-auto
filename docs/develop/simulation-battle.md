# 模拟室单战父流程

`SimulationBattleRun` 将已完成的[详情与选队交接](simulation-entry.md)、[出战与子战斗](simulation-deploy.md)和[结算领奖](simulation-settlement.md)串成一次内部单战。`after_entry` 消费已就绪的 `EntryRun`；`new` 仅接收尚未执行、输入已释放且冻结配置一致的 `DeploymentRun`。父子共用运行 ID、取消句柄和活动预算，不建立第二个运行槽，也不直接登记体力计划次数或应用成功。现由[完整挑战父流程](simulation-challenge.md)接续卡片 / 电量准备和详情 / 选队，关卡验证前置继续保留。

关卡回执仍必须明确 `selection_verified=true`。目前生产 `MissionRun` 固定提供未验证回执，本父流程没有增加证明生产者或绕过开关；体力应用、桌面和 CLI 的带输入运行入口继续关闭。测试中的已验证关卡只用于隔离回放。玩法与区域继续依据参考仓 `CombatSimulation`、`Deploy`、模拟室、通用出战和战斗画面资料，没有新增推测的颜色或按钮区域。

## 单战与输入交接

父流程依次处于 `Deployment`、`Combat`、`Settlement` 和 `Done`。出战先复验冻结关卡与实际足额电量，沿用低等级确认、前移和新战斗帧证明；子战斗保留首次输入前已经编译的脚本，要求实际进入战斗及连续新帧结果；撤退不进入领奖。结算分开保存完成、实际奖励、奖励确认及返回详情，返回所需电量必须与本次冻结卡片方案一致。

阶段交接先保存检查点，再处理控制请求及剩余预算，然后才交接控制器。实际游戏使用冻结窗口和截图方式，通过 `NativeSession::handoff_game` 维护唯一原生槽位：界面使用前台键鼠与 CPU，战斗采用冻结输入方式和推理设备，领奖再回到前台 CPU。销毁或重建前等待旧 Tasker、控制器和输入释放，丢弃旧识别器，不能重叠两个控制入口或 GPU 路径。交接失败保留错误，不继续后继。

隔离模式仅复用已有前台 CPU 控制器；在首次输入前拒绝手柄或 DirectML 配置，不能用它宣称真实设备切换已通过。外层仍须在任务输入前完成混合输入恢复登记、窗口确认和运行槽管理。本轮没有新增输入动作、恢复版本或资源 schema。

## 资源、暂停和结果

构造时完整校验模拟室、出战、结算及战斗资源，并冻结清单哈希。执行、继续和阶段切换重新校验；下游模型或节点发生变化也会在首次出战前拒绝，不等消费后才发现缺失。暂停期间外层可以销毁原生槽位，继续会重新校验并加载资源，不沿用旧句柄的装载缓存。

暂停沿用各子流程的意图和投递回执。即使子流程已经返回完成、父流程在终态保存时才收到暂停，也会撤销旧到达或返回证明，继续后读取新帧；已经提交的出战、前移、完成和领奖不重放。战斗暂停保留脚本调度器，但重新建立帧和结算确认。停止优先于继续，单战结束不终结更外层应用的共享控制句柄。

执行期的资源校验、保存、识别、控制器交接和输入收尾均计入同一父预算，暂停时间不累计；更外层须在构造冻结资源之后计算并传入自身剩余预算。原生操作仍须等候安全收尾，预算不代表强制中止原生线程。原生战斗达到父截止时间返回 `TimedOut`；明确保存失败不会因同时超时而被吞掉。任意保存失败、停止、超时或输入未释放都不能生成正常单战证明。

`proof()` 仅在父流程实际返回 `Completed`、输入已释放且没有待处理请求时提供运行 ID、冻结关卡与领奖后电量。可见的完成画面或子流程快照不能代替该证明。外层仍须保存结果、核对对应计划和单战身份，才可登记运行次数。当前快照用于发布、外层存档和诊断，没有由任意旧 JSON 快照恢复执行的入口。

新增回放复用组合详情、出战、通用战斗结果及既有奖励留档，通过真实 Maa SDK 的隔离控制器推进。没有连接游戏或修改用户配置。协议 v46、导入预览 v19、执行资源定义和正式可用标记保持不变。关卡选中证明、传送与准备的完整父任务、体力运行登记、真实键鼠 / 手柄和设备切换、按钮悬停影响及全部实机验收继续保留；既有 Maa 队列交接时序待查项也不因隔离回放关闭。
