# M4 Rust 战斗开发

M4 使用 Rust 执行条件脚本，Maa 唯一控制器提供截图和动作；战斗模板直接调用 OpenCV，闪光使用原始 ONNX Runtime 推理，颜色及轮廓规则由 Rust 执行。结算 OCR 与其他日常识别继续经过现有 Maa 接口。日常与战斗共享现有运行槽、事件、历史及暂停 / 停止入口。真实游戏、延迟指标、长时间稳定性和声音阈值对照均保留为验收，不以自动回归替代。

## 脚本与时钟

保留 YAML 的场景、触发器、优先级、时间窗、值范围、嵌套 handler、继承打断条件、状态及动作模板和旧 `data` 参数。表达式中的 `&` / `|` 与参考解析器一样从左到右结合，括号和 `!` 优先；空表达式为真。加载时展开全部模板，拒绝循环、未知指令和字段，并把文件与字段路径包含在错误中。禁止加载失败后运行部分脚本。

加载支持 YAML 锚点、`<<` 合并键和模板说明字段。`state_template` 与外层 `states` / `interrupt_states` 同时存在时保留外层条件，避免旧加载器丢失条件；不允许同时再写 `operations` 或 `sub_handlers`。旧样例中设置 / 清除状态误带的方括号和中文引号在载入时去掉，写入表达式实际使用的状态名。此两项修正与旧程序的静默忽略行为有区别，合并和未合并脚本均应列入正式回放验收。未知业务状态与角色名称在启动前拒绝，`自定义-` 状态允许扩展。

调度与识别使用单调时间。状态记录保留观测时间，过期或前一代识别结果不得更新状态。暂停先取消执行、等待控制器并释放输入，继续时清空识别缓存和待执行动作，重新识别；不重放暂停前动作。脚本中的未来状态时间与负数窗口继续支持。

## 调度与输入

2026-10-31 的同机实跑中，Python 有效截图约 29.5Hz，Rust 1854 个攻击按钮识别起点的平均间隔约 103ms（约 9.7Hz），P95 144ms。两者统计起点、音频工作量及构建方式未完全对齐，但串行识别后额外等待 20ms 和在输入循环中等待整轮识别，是已确认的调度差异。

本轮优化先覆盖独立自动战斗：单个后台工作线程复用当前资源、原始闪光缓存和识别互斥；主线程保持唯一输入执行权。工作线程最多处理一个在途任务，主线程只保留最新待识别截图，不能堆积旧图。只把实际完成的识别计入 `frames`；继续使用截图原始时间判断过期。切人及重读时递增观察代际，旧结果不得覆盖已经发送切人的队伍顺序。退出先释放输入，再取消并等待工作线程，确认资源空闲后才发布终态。应用内带页面守卫、结算和锄大地 HUD 校准的战斗仍采用现有同步路径。

独立战斗在创建会话时直接载入战斗包，应用内流程则通过 `load_combat_bundle` 追加。后台读取器核对识别器已校验的包路径与会话实际载入的路径，两种入口都应接受；只有通用资源且未追加战斗包时仍须拒绝。此前只检查追加加载标记，导致真实独立战斗启动立即误报“未载入战斗资源”；完整通用脚本回归现按真实入口分别创建会话与识别器，另覆盖追加加载和资源不匹配。

闪光识别成功后先发布本帧攻击按钮证明和闪光状态，不等待头像、能量或目标检查；完整结果移除已发布的闪光，防止同一观测重复出招。闪光调度和待投递输入优先于下一次截图；定时释放按最近截图耗时预留时间。截图、识别和输入仍共用已有控制器约束，实际操作系统排队耗时不承诺消失。

第一轮模板优化按同帧 ROI 缓存裁图，仅将局部像素交给 Maa，ROI 改为裁图原点；阈值、方法、模板和掩码不变。局部匹配必须与原全帧 ROI 结果对照。调度间隔从截图开始计算，不在识别完成后重复增加等待。验证重点为吞吐、长识别期间的松键、停止先释放再等待、旧代际不出招及原有 BUFF / 队伍恢复行为。

后续替换战斗识别路径：模板在资源校验后一次解码为 BGR 并预计算绿色掩码，`CombatVision::match_template` 直接调用固定 OpenCV 4.12.0 的 `TM_CCOEFF_NORMED`。匹配借用截图 ROI 的原始指针与整帧步长，结果复用线程局部有界缓冲，不再裁图复制、构造逐模板 JSON、投递 Maa Tasker 或读取任务详情。最高分、严格大于阈值、NaN/Inf 跳过以及原路径 NMS 的 0.1f 分数下限保持一致；全有效掩码继续使用无掩码路径。独立与应用内战斗共用该实现，闪光、颜色/轮廓、调度和输入协议保持现有算法。

小型 C++ C ABI 桥接使用固定上游 4.12.0 头文件；SDK 路径、哈希及 OpenCV 版本检查通过后，才从同一已载入 DLL 解析 Mat 构造、销毁与匹配三个入口。构造与销毁不跨运行库交接所有权；同步调用结束前不保留 Rust 指针，C++ 异常转为错误返回。没有静态 OpenCV import、额外 OpenCV DLL 或 Python 运行依赖。构建使用现有 MSVC C++ 工具链，固定 SDK 升级时须同步核对头文件、导出签名和数值回归。来源、头文件哈希与许可证见 `crates/maa-adapter/native/opencv/` 和[第三方说明](../migration/third-party.md)。

一次只有一条动作序列。普通场景只在空闲时轮询，触发场景按间隔与优先级抢占；同一场景不抢占自身。父子 `interrupt_states` 合并。所有动作经单一执行器投递；抢占、暂停和停止先释放上一序列持有输入，失败则结束任务并保留恢复记录。按下、点按、松开、重复、前后等待、角色切换、状态修改与转向共用该规则。

无时长的按下可跨 handler 保持，显式松开、角色切换、抢占、画面失效、暂停和停止负责释放。逻辑按键共享物理按键时按持有关系合并，方向摇杆叠加，扳机取最大值；转向结束只移除转向持有。定时松键优先于可能阻塞的下一次截图识别。周期锁定与转向等待主序列空闲后进入同一队列，避免另一线程抢用输入。动作事件在对应原生按下 / 松开确认后写入，实际时序与旧版点按完成时间的差异仍需验收。

M5 增加供应用流程调用的 `CombatRun::new_segment / execute_segment`：共用外层控制句柄，先确认进入战斗，再用连续两张新帧确认普通完成或撤退。子战斗释放输入后交回结果，由外层处理结算按钮、检查点和整个应用的暂停 / 终态；不能直接将子战斗进度当作整个应用的成功。原有独立自动战斗仍持续运行到中断或超时。资源预加载、交接边界及离线验证见[情报板共用基础](remaining-game-apps.md#情报板开发中的交接规则)。

## 识别与声音

2026 年 10 月 31 日，普通自动战斗运行 `856889ff-ae71-4b43-a13c-4dee3035cad6`（脚本修订 `d0646c565844`）在约 71 秒内只处理 75 帧，47 帧超过默认 250ms，执行 26 个动作，结束时帧龄为 819ms。此记录证明普通战斗仍未达到可用要求。全角色头像逐模板串行扫描、三人队伍额外扫描双人槽位，以及慢帧清除自定义状态都会扩大差距。

修复采用每槽位有界发现：优先重新匹配上次命中的模板和已发现成员，再分帧扫描其余候选；缓存只减少候选，不能代替新截图匹配。三人槽位已完整命中时不再识别双人槽位。无命中不能将发现进度归零，否则候选列表末尾的角色永远无法被发现。慢帧仍停止当前动作并释放输入，但保留已执行的自定义状态和场景冷却，避免重复补 BUFF；真正暂停继续仍按原规则清空会话。普通战斗留档须单独检查发现阶段与稳定阶段的帧龄，不能用锄大地画面测试代替。此改动不等于已完成识别与动作的独立调度，实机反应速度继续需要验收。

随后运行 `4f785472-0bc2-4bb6-9401-af7ad9aae320` 在约 90 秒后因“切换目标 叶瞬光 不在已识别队伍中”失败；795 帧仅 2 帧超时，故障发生在快速支援时把短暂只读到露西的画面当成单人队伍。修复须区分当前命中的头像与已确认的队伍：单次漏识别保留槽位及已知成员，未知位置仍不产生角色状态；只有新读到的前台和其余可见槽位与已知顺序相符时，才使用已知队伍推算切换方向。缺少切换目标或顺序不确定时释放输入、撤销当前动作余项并重新识别，不能报错结束，也不能向错误角色继续施放动作。真正重新开始或暂停继续后重新建立队伍信息。

识别层复用固定 SDK 中的 OpenCV 及已有闪光原始推理，统一提供角色、按钮、连携、快速支援和目标状态。识别节流在引擎内完成，候选角色失配时分帧重新发现。闪光 CPU 与 DirectML 推理继续服从适配层的推理互斥和 GPU 租约，声音线程只提交状态。

直接 OpenCV 模板匹配负责角色头像、普通攻击按钮及模板型角色状态；Rust 保留旧 RGB / HSV、灰度长度、掩码、连通块与轮廓组合规则。锁定目标需要嵌套轮廓的中心邻近关系，连携条需要外轮廓周长，继续使用 `imageproc`。当前转换包的模板数量由清单确定，本次直接匹配回归覆盖 539 个模板；原始迁移留档为 60 名角色、527 个模板、9 个战斗入口（含开发用闪避助手）、7 个旧闪避入口。只需要普通攻击按钮或闪光的脚本会跳过角色全量扫描；不需要闪光的脚本不创建闪光推理。角色、快速支援和连携候选有独立节流，候选缓存不能充当新画面的识别证明。

声音路径由 Windows 输出回录产生 PCM，转单声道与 32 kHz 后，采用四阶 1 kHz Butterworth 高通、双向滤波、无去均值标准化及 FFT 相关。配置和报告明确保留算法与阈值，靠近阈值的真实音频仍须对照旧版。设备错误应显示并使当前声音会话停止，不自动改选其他设备继续输入。

静音包显式填零；断续、积压与超过 150 ms 的停顿清空旧音频并重置检测器。回录缓冲有 0.5 秒上限。相关性按模板长度归一，严格大于阈值才触发，触发后清窗并去重。非 32 kHz WAV 使用固定窗化 sinc 重采样，回录的格式转换由 WASAPI 共享模式完成；两者与旧 librosa / 设备链路的实际差异没有用纯信号测试代替。声音默认关闭，默认阈值 0.1 仅作为旧配置起点。手柄转向使用右摇杆与显式速度参数，键鼠使用 Maa 相对位移，实际灵敏度与方向须分别标定。

## 桌面、配置与恢复

侧栏“自动战斗”读取当前账号的 `combat` 设置，支持闪避 / 完整战斗、脚本、合并文件优先级、自动终结技状态、截图间隔、CPU / DirectML、输入方式、声音和转向设置。保存后核对当前账号并确认输入，才可开始。主线程界面不参与动作定时；全局 F9 暂停 / 继续、F10 停止仍进入同一个引擎入口。运行状态与停止按钮置于页面顶部。

配置保存在数据目录 `config/accounts.yml`，账号复制、备份恢复和旧配置导入保留这些字段。旧 `battle_assistant.yml` 与 `game.yml` 中的脚本名、背景手柄、点按时长及可转换键位会迁入；无法转换的自定义键位保留原文件归档并返回警告。战斗脚本内容需在战斗页单独预览、确认导入。导入验证全部模板及合并 / 未合并入口，将原字节保存到 `combat-scripts/snapshots/<内容身份>/`，通过原子替换 `active.json` 选择；来源变化或选择变化会使旧预览失效，同名入口采用导入快照。账号备份只恢复设置，不回滚脚本快照。

启动冻结账号、设置与脚本修订，运行记录保留该修订。战斗与日常共用运行槽和控制器交接。桌面在启动前保存 v8 输入恢复计划，覆盖本次所有自定义映射；未收到同 ID、相符账号上下文与输入释放证明时保留恢复登记。释放失败阻止新任务，历史写入失败支持重试。继续使用同一运行 ID，清空旧调度代际、识别和动作队列，重新采集战斗画面；不回放暂停前输入。

## 构建与离线入口

开发构建读取参考仓和固定模型缓存，发行运行不需要 Python 或参考仓。`prepare-engine.mjs` 自动准备战斗包；Tauri、便携包和 schema 4 完整运行资源包均包含战斗资源，复制前后执行独立校验，保留 `accepted: false`。资源兼容规则见[运行资源包](runtime-resources.md)。

```powershell
cargo run -p od-tools --locked -- combat-bundle --reference E:/Code/ZenlessZoneZero-OneDragon
cargo run -p od-tools --locked -- types
cargo run -p zzz-engine --locked -- combat-bundle-check
cargo run -p zzz-engine --locked -- combat-inspect --image zzz-od-test/screens/战斗画面/默认.webp --dodge-only
cargo run -p zzz-engine --locked -- combat-replay --scripts resources/generated/combat/scripts --script 闪避助手 --events artifacts/m4-replay-events.json
```

`combat-bundle-check` 不加载 SDK；`combat-inspect` 只对固定图片识别；`combat-replay` 只运行确定性调度，不采集音频或发送输入。回放文件是 JSON 帧数组，每帧包含 `at`、`updates`，可选 `complete`、`pause`、`resume`；状态更新包含 `name`、`at` 和可选 `value` / `add` / `time_add` / `clear`。命令输出明确保留未验收标记。真实运行入口为 `combat --hwnd <窗口> --instance-id <账号> --allow-input`，使用保存的设置，Ctrl+C 请求统一停止收尾。

## 开发验证

2026 年 10 月 31 日新增普通战斗回归：同一张 `screens/战斗画面/默认.webp` 在修复前，前六次完整头像发现耗时约 1051..1364ms；修复后 40 次普通识别为 74..115ms，开启闪光并完成模型冷启动后为 100..104ms。遮挡头像的合成画面验证缓存身份不会被当作新匹配。完整“全配队通用”脚本在模拟控制器上运行 60 帧，0 帧丢弃、24 个动作，并发现完整队伍；另插入一次 300ms 截图延迟，确认输入释放且不重复补 BUFF。上述数据为本机固定图与模拟输入结果，尚未验证真实游戏的闪避成功率、连携与切人响应。

```powershell
cargo test -p zzz-engine --lib combat::tests --offline --target-dir target/exploration-build
cargo test -p maa-adapter --test combat_vision --offline --target-dir target/exploration-build -- --ignored --nocapture
cargo test -p zzz-engine --test combat_runtime --offline --target-dir target/exploration-build -- --ignored --nocapture --test-threads=1
```

首轮修复的 3 项战斗回归、相邻 9 项地图探索运行回归（含 Python 开发脚本）及引擎开发构建通过，已同步到桌面开发用 sidecar 并核对 SHA-256 一致。严格 Clippy 检查仍被 `maa-adapter/src/map_exploration.rs` 的既有 `items_after_test_module`、`needless_borrow`、`collapsible_if` 警告阻挡，不能记录为全量静态检查通过。

针对第二次快速支援失败，本轮 2 项队伍顺序测试、1 项固定图识别回归（新增只遮挡后台及头像恢复场景）、3 项模拟输入运行回归和 1 项相邻锄大地战斗识别检查通过。命名切人在队伍尚未发现时不会报错或继续施放后续技能，重新识别后能恢复执行；完整通用脚本回放 61 帧、0 慢帧丢弃、31 个动作。普通固定图帧龄为 60..130ms，闪光热态为 78..85ms。开发引擎再次编译并同步，SHA-256 一致；真实游戏的长时间运行仍待复测。
