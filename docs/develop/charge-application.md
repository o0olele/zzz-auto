# 体力应用历史与完成证明

继续完整体力目标，沿用用户暂不启动游戏、保留实机验收的选择。本段接入已有内部父流程的应用记录，不开放尚未接通的桌面或应用组执行入口。原生控制器仍由同一 ChargeWorker 持有；记录适配器不另建会话，也不能用反序列化快照恢复输入。

通用历史有 1 MiB 上限，体力消费日志最多 8 MiB，因此 RunRecord 只增加可缺省的紧凑体力摘要：冻结运行身份、应用状态、阶段、资源、活动耗时、输入释放、计数及完整检查点指纹。完整副本结果仍在 runs/charge 中，由现有先日志后配置提交机制保存，不复制进应用历史。

摘要绑定同一运行 ID、账号、应用组、启动修订和游戏日。完成记录须复验对应日志、完整结束选择及摘要指纹；配置提交未完成、无计划、资源不足、周常或目标阻挡、待验证、停止和超时均不提供每日成功。完整成功须来自私有父实例的已保存正常终态、实际返回大世界及输入释放。原版体力记录每次运行重置状态，后续正式入口仍需保留每次运行语义，本段不改变通用运行策略。

运行前保存应用记录，失败则不发出输入。过程记录保存失败按原父流程的保存错误处理，释放输入并保留失败；已取得的消费事实仍由原日志恢复。最终历史保存失败冻结原结果，只允许补存，不重新执行。开始时拒绝复用已有历史运行 ID；暂停继续沿用同一实例，停止后补存也不恢复输入。

最终结果与控制请求通过同一把控制锁确定先后：已有暂停或停止时保留原请求，撤销尚未提交的应用成功；成功封存后只补存该结果。外部仅取得请求句柄，不能清除控制请求或伪造队列静止。历史与配置必须属于本次冻结的同一数据目录，补存不能更换目录；首次记录必须先于私有父实例执行，收尾发布耗时计入父预算。

旧 RunRecord 没有体力字段时继续按原规则读取。应用历史页沿用现有账号、应用、游戏日及结果筛选；体力超时仍归入超时过滤。每日成功同时复验运行时间、账号上下文及体力完成证明，缺失或损坏的完成日志不能当作可靠成功。

可靠无活动判断、模拟室生产选中证明及完整消费、正式独立与应用组运行入口和真实游戏验收继续属于完整目标，不能由记录接入替代。
