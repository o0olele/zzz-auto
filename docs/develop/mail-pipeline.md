# M2 邮件 Pipeline 试运行

2026 年 10 月 15 日按用户决定开始 M2，M1 保留待验证项。完整邮件流程已接入桌面的“原生诊断 → 邮件流程试运行”，与其他原生任务共用运行槽、工作线程、输入清理和恢复监督。专用资源包与业务检查点已有离线回归；2026 年 10 月 16 日大世界和菜单起点均获实机测试通过反馈，暂停、异常等场景继续验收，应用列表中的邮件继续标为待迁移。

## 构建与复跑

在主仓根目录执行，不依赖 Python：

```powershell
cargo run -p od-tools --locked -- mail-bundle --reference ../ZenlessZoneZero-OneDragon
cargo test --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/validation --locked --test mail_rewards -- --test-threads=1
```

默认输出为 `resources/generated/mail/`。来源为参考仓 `email.yml`、`menu.yml`、`normal_world_basic.yml` 中十个区域及其模板。OCR 使用 `models.lock.json` 固定的 ppocrv5 检测、识别模型与字典。构建器核对模型原始字节，将旧矩形转换为 Maa ROI，保持 1920×1080，不缩放模板。独立二值掩码的 0 像素转换为 RGB `(0,255,0)`，255 像素保持原值，显式启用 `green_mask`，模板方法为 5。

`resources/mail/pipeline.json` 是手写流程源，构建后才写入生成包的 `pipeline/`，避免默认健康检查包加载未生成的区域引用。构建器将固定 ROI / target 别名展开为数组：Maa 的字符串 ROI / target 是识别结果引用，不能代替区域配置坐标。

`mail-manifest.json` 保存源 YAML、模板、掩码、手写流程和生成文件的 SHA-256，记录 SDK 与坐标基准。相同输入可重复生成；来源与输出不得重叠，全部输入验证后才写入；输出含外来文件或符号链接时拒绝，不删除用户文件。清单保留 `accepted=false`，直至实机验收。

普通 `convert-screen` 仍保留既有 LCS、掩码和颜色转换限制。本包只提供邮件所需区域的精确正则和掩码转换，不代表所有画面或 LCS 已完成等价验收。

## 桌面试运行

开发运行先按上述命令生成邮件包，再在 `apps/desktop/` 执行 `npm run tauri dev`。邮件包不进入 Git。Release 构建会在构建机生成并校验邮件包，便携包和 NSIS 资源配置均包含 `resources/generated/mail/`，测试机无需安装 Rust、参考源码或模型缓存。

跨电脑使用 `scripts/package-portable.ps1` 生成的完整客户端 ZIP；同时输出 `mail-resources` 资源补丁 ZIP。已有本版邮件试运行客户端缺资源时，退出客户端，将资源补丁直接解压到 `zzz-desktop.exe` 所在目录，应得到 `resources/generated/mail/mail-manifest.json`、`pipeline/`、`image/` 和 `model/`；保留原有 `data/`。旧版客户端若没有邮件入口，请改用完整新包。不要把补丁额外套一层同名目录，也不要只复制流程 JSON 或模型。

资源补丁只能配合相同流程版本的引擎。流程定义修改后会改变内置哈希，必须使用包含新引擎的完整客户端；不能只覆盖 JSON 绕过校验。2026 年 10 月 16 日的大世界 Alt 等待修复属于此类更新。

构建机默认读取相邻 `../ZenlessZoneZero-OneDragon`，可用 `ZZZ_AUTO_REFERENCE` 指定其他参考仓位置，固定模型仍须预先准备在 `sdk/models/`。`-SkipBuild` 也会使用已构建引擎校验资源，不允许把缺资源或不匹配的包发布出去。`zzz-auto-engine.exe --root <客户端目录> mail-bundle-check` 可独立验证资源，不加载 SDK、不连接游戏、不创建用户数据；`check-environment.cmd` 同时检查 SDK 和邮件资源。

1. 启动游戏，设为 1920×1080 客户区，连接游戏窗口并检查截图。从大世界、菜单或邮件列表开始。
2. 打开“原生诊断”，设置邮件超时和启动 / 继续延时，勾选本次输入确认，再点击“开始邮件流程”。默认业务超时 60 秒、准备延时 3 秒；在延时期间切回游戏并保持前台。当前只使用前台键鼠与 CPU 推理。
3. 点击“暂停邮件”先显示暂停中，只有 Tasker 静止且输入明确释放后才显示已暂停。继续保留同一运行 ID 与领取检查点，延时期间再次切回游戏。暂停时间及准备延时不消耗业务超时。
4. 点击“停止邮件”后等待停止收尾；超时、停止和失败均需要确认释放结果。终态不会自动重跑，新一轮须重新确认输入。引擎异常退出后先完成输入恢复，再人工检查游戏状态并重连，不续跑旧任务。

每段流程前重新核对窗口 PID、尺寸、权限、新截图与前台状态；校验不通过时不投递该段按下。运行时先校验包内路径、文件数量、SHA-256、固定 OCR / 字典、1080p ROI 和引擎内置流程定义。即使重新计算清单哈希，也不能加入任意动作或后继图；版本不匹配时需要重新生成。校验完成后作为额外资源层载入，不替换基础健康检查资源。

## 流程与识别

依据为旧仓 `docs/game/screens/邮件.md`、`大世界.md`、三个 screen_info 和 `EmailApp`。测试复用大世界、菜单、可领取列表、已领取列表和奖励弹窗五张真实截图；自定义控制器在点击后延迟两次截图再换帧，交给真实 Maa Tasker 完成识别、轮询与动作。

完整路径：大世界持有 Alt 点击菜单 → 释放 Alt → 邮件 → 核对标题和全部领取 → 判断按钮状态 → 领取 → 核对奖励弹窗 → 确认 → 核对已领取列表 → 返回菜单 → 返回并核对大世界。也可从菜单或列表进入；未知画面超时，非本次领取产生的通用弹窗不自动接管。

领取后按钮可能先变灰，奖励弹窗稍后才出现。返回列表时继续优先识别奖励弹窗，关闭列表后的等待也检查弹窗；仅本次已有领取尝试时进入确认，再核对已领取列表并返回。运行时以固定任务覆盖补充这两处分支，既有邮件包定义与哈希校验保留。2026 年 10 月 21 日运行 `64546efa-2b33-410a-85e4-1918ce50df87` 暴露了这次时序问题：`AfterClaim` 先识别到 `Mail.Empty`，进入 `ReturnList` 后奖励出现，旧流程只等待 `Mail.CloseList` 并失败。

大世界入口按旧控制器时序，Alt 按下后至少等待 200ms 再按下鼠标，让游戏先解锁光标。`Mail.WaitAlt` 用九次无输入动作与八段 25ms 间隔实现，避免一个不可及时中断的长等待；暂停 / 停止后仍等待原生队列结束并显式释放 Alt，继续时重新识别。测试控制器在菜单鼠标按下时检查等待长度，而不是等鼠标抬起后才检查；也覆盖此等待期间暂停、停止与继续。

“全部领取”变灰后仍能 OCR 命中。可领取要求列表锚点与 RGB 黄色像素；已领取要求列表锚点与文字区域灰色像素。黄色采用 `[150,140,0]..[255,255,100]`、至少 150 像素；灰色采用 `[80,80,80]..[190,190,190]`、至少 150 像素，文字 ROI `[154,1012,107,32]` 来自已有邮件文档。颜色方法显式为 4（RGB）。不能用组合识别引用的节点级 `inverse` 代替子识别取反。

颜色只在现有两张列表图上验证，主题、亮度、悬停、过场和版本变化仍需实机证据。弹窗要求“获得”标题及“确认 / 确定”按钮；“确定”变体没有真实截图，其画面、位置和后续状态均不记为已验收。

## 暂停与结果

`PipelineControl` 区分请求和执行确认。向其他线程提供的 `PipelineRequest` 只能请求暂停 / 停止，不能清除取消或确认队列静止。继续必须等待执行方确认已暂停，停止优先且不能被继续覆盖。`MailRun` 保存运行 ID、阶段、领取尝试、已见奖励、返回阶段和有效耗时。

`execute()` 是固定图入口，桌面工作线程使用 `execute_game()`；二者运行到完成、失败、超时、暂停或停止。每段沿用 M1 的停止与清理：等待 Tasker 静止、显式释放 Alt 和鼠标通道、等待 inactive；释放失败保留失败与待清理责任。请求本身不能被显示为已经暂停或停止。

暂停后调用 `resume()` 再 `execute()`。ID、领取检查点和有效耗时保留，暂停时间不消耗超时；继续时强制重新截图：奖励弹窗继续确认，已领取列表继续返回，返回途中的菜单或大世界接续收尾。终态禁止直接重跑，下一轮使用新 ID。暂停期间请求停止后，调用 `execute()` 确认收尾，不能用继续清除停止。

领取检查点在投递前设置；只有明确没有 task ID 才清除。投递后即使没有成功节点也可能已生效，继续时不再次领取；若仍显示可领取，等待领取后状态直至超时，并报告不确定结果。检查点目前在进程内保留，可以序列化查看，没有跨进程自动恢复入口。成功必须到达每段声明的业务节点，SDK Succeeded 不能单独证明整个应用完成。

`NativeSession::pipeline_events(capacity)` 提供有界展示队列，仅保留任务、Pipeline 节点与动作的消息名、任务 ID 和节点名。回调用 `try_send`，不等待 Tasker、不取得业务锁、不输出原始详情、OCR、图片或 focus；满队列计入 `dropped()`。业务检查点和终态在原生收尾后读取 SDK 保存的任务详情，独立于可丢弃的展示事件。旧 M1 诊断不额外读取节点详情。

任务事件和节点事件分别注册 Tasker sink 与 context sink，共用同一个有界队列。生成的业务节点显式设置非 null 的空 `focus`，使固定 SDK 发送节点进度，不开启全局调试。会话结束时先注销 context 和任务订阅，再清理其余回调和 Tasker，保证原生回调不引用已释放的闭包。

`Node.PipelineNode` 表示流程轮次进度，不能据此猜测某个动作已经完成。动作展示使用 `Node.Action`，回归明确检查 `Mail.ClickClaim` 的 `Node.Action.Succeeded`；业务完成仍读取 SDK 保存的节点结果。会话销毁后两个事件接收端都必须断开，不能有闭包继续持有发送端。

## 协议与恢复监督

协议 v8 增加受限的 `StartMail { config, allow_input }`、`Pause { run_id }` 与 `Resume { run_id }`，不接受任意 Pipeline JSON。`RunRecord.mail` 保存阶段、领取尝试、奖励观察、有效耗时和释放证明；旧记录缺少此字段时按 `None` 读取。运行槽增加 `pausing`、`paused`，暂停任务仍为非终态，禁止其他任务、截图、重连和权限切换。超时保留 `mail.state=timed_out`，槽状态为失败。工作线程把原生展示事件转成带运行 ID 的有序事件，并将暂停与终态写入 `data/runs/<id>.json`。

桌面在发送开始命令前同步写入 v2 输入恢复计划，只允许固定的前台 Alt 与鼠标左键释放组合；v1 单动作计划继续兼容。记录在暂停期间保留，继续前核对磁盘文件与当前运行 ID / 缓存计划。丢失或被修改时断开旧引擎并拦截新输入，只有匹配运行的终态和 `mail.inputs_released=true` 才能清除。缺少释放证明的失败同样进入恢复拦截。

独立恢复等待原引擎退出，只尝试释放，不重放领取或继续业务。释放失败保留记录和错误；成功后仍需人工核对游戏。检查点只用于当前进程内继续，保存的运行 JSON 不提供跨进程自动恢复入口。`Engine::for_mail_fixture` 是独立测试仓注入会反应控制器的入口，不通过 CLI / IPC 开放。

## 验证与后续

测试在独立测试仓，覆盖资源重建、哈希、坐标、掩码与字典、来源保护、五种画面、完整多帧推进、满事件队列、重复执行、领取 / 确认中暂停、领取效果不确定、停止、超时及动作 / 释放失败。设置 `ZZZ_M2_MAIL_REPORT` 为新的 JSON 文件路径可以保存固定图原生观察；未设置时不会改写验收档案。

`mail_rewards` 用本次用户提供的奖励截图和已有真实列表、菜单、大世界留档，经真实 Maa Tasker 验证按钮先变灰再弹奖励、关闭列表时才弹奖励、正常奖励、无奖励、非本次弹窗拒绝确认和确认前暂停继续。断言领取和确认各执行一次，最终返回大世界并释放输入；受控截图时序不代替本次实机复测。

新增集成回归使用真实 Engine 工作线程及 Maa Tasker，验证领取后暂停、同 ID 继续、运行槽互斥、结果落盘、事件序号、继续 / 停止竞争及暂停后退出；资源伪造测试修改哈希后仍拒绝额外动作。桌面恢复测试验证落盘先于请求、暂停保留、继续前丢失记录、缺失释放证明和恢复计划限制。另用屏幕外且不激活的 Win32 测试窗口确认真实游戏入口在前台检查失败时没有投递按下，不向全局输入流发送按下。
