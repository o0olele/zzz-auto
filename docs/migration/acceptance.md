独立 Rust 回归与前端测试入口见根 README。主仓没有内联测试模块或测试目录。日志缓存有容量限制，丢弃统计包含回调拥堵；原生回调不等待自己的 Tasker。

当前验证结果：11 项 Rust 回归、2 项前端流程检查通过；`cargo fmt`、严格 Clippy、TypeScript 与 Vite 生产构建通过。Tauri 原型输出为 `target/debug/zzz-desktop.exe`；`target/release/zzz-engine.exe` 也已生成。构建结果不代表实机、安装包或发行验收通过。

一次 CPU 原型样本：正常 Pipeline 2639 ms，入队 170 μs；100 ms 后取消的样本总计 226 ms，停止收尾 123 ms。这只证明本机该无输入流程的可运行性，样本数不足以计算代表 P95，不能证明游戏输入的 250 ms 目标或模型兼容。

## 已发现的不兼容与处理

1. 固定官方 Windows SDK 包未包含 `MaaDbgControlUnit.dll`；绑定的 `new_dbg` 创建失败。离线入口改用官方自定义控制器，提供固定 PNG 画面，不支持模拟点击换帧。完整邮件流程仍需要会响应动作的测试控制器。
2. 固定 SDK 对参考 WebP 通过 `set_encoded` 返回成功但尺寸为 0×0。离线入口用 Rust `image` 解码后编码 PNG，原生游戏截图仍经 Maa；这不是另建识别引擎。限制文件大小、解码尺寸和内存。
3. 绑定 1.25.2 的 `new_custom` 未保留回调 Box 的销毁所有权。适配器使用官方 sys 与回调表，显式持有回调，并在控制器销毁之后释放。
4. SDK `MaaTaskerPostRecognition` 返回 `MaaTaskId`，绑定 1.25.2 的 `job.get` 直接当成 `MaaRecoId`，详情查询失败。适配器用 task → node → recognition 获取结果，真实模板回归覆盖该路径。
5. 旧 OCR 的 LCS 语义与 Maa `expected` 正则不同；独立模板 mask、颜色过滤和模型预后处理尚未验收。生成资源带差异报告，全部游戏应用继续返回 `not_migrated`。

## 尚未通过的阶段条件

当前 `windows` 未发现运行的 `ZenlessZoneZero.exe`，参考目录未发现 ONNX 模型。继续 M1 需要准备旧版实际使用的 OCR 模型 / 字典、闪光 / YOLO 模型与预期输出，并打开游戏。

- 前后台截图与输入、窗口失效、权限不匹配、权限提升及前后台按住 / 释放。
- Xbox / DS4 与 ViGEmBus、摇杆、转向，以及崩溃后的独立输入恢复。
- 相同旧模型、输入和参数下的 CPU / DirectML 输出与延迟对照，GPU 使用时段互斥。
- 可反应的邮件流程语料、领取确认与物品爆满分支、重复领取检查和安全暂停恢复。
- 音频触发、未触发、阈值附近录音及旧算法输出；当前仅有模板 WAV。
- 同机旧版性能、30 个测量样本及 P50 / P95；两小时战斗与百轮生命周期稳定性。
- 配置导入、账号、应用组、HTTP / MCP、战斗、工具、插件和发行更新的各阶段验收。

输入探针最长按住两秒。键鼠 `--key` 使用 Win32 VK 1..254；Xbox / DS4 使用官方 XUSB 位掩码，例如 A / Cross 为十进制 4096，LB / L1 为 256。按键释放经过队列完成确认；摇杆与崩溃恢复尚未开放或验证。管道断线后取消任务并等待收尾；原生阻塞时不能宣称已在限时内完成退出。

当前 debug 桌面可执行文件只适用于本工程开发机；NSIS 配置已建立，但安装包、签名、离线模型完整包、便携版与干净环境未通过 M7 验收。

## 2026 年 10 月 13 日便携测试包

已构建 release 桌面与引擎，提供 `scripts/package-portable.ps1` 生成 Windows x64 ZIP。包内包含 19 个固定 Maa DLL、同一套 VC++ x64 可再分发 DLL、微软签名验证通过的 WebView2 联网安装器、Pipeline、应用登记、许可证和启动 / 诊断脚本；不含开发运行时、模型或本机用户数据。

`portable.flag` 让桌面从自身目录定位资源与引擎，数据保存在解压目录的 `data/`。新增独立路径回归覆盖移动后的中文目录、开发目录隔离及安装模式保留，严格 Clippy 与 release 构建通过。

已将 ZIP 解压到不同的中文与空格路径，核对 54 个文件 SHA-256；从包外工作目录调用包内引擎，SDK `doctor` 与真实无输入 Maa Pipeline 通过。桌面 / 引擎的 PE 依赖已检查，所需 VC++ DLL 随包提供。该验证仍在本机执行，其他电脑的游戏、驱动、WebView2 及干净系统表现由后续实测确认，不算 M7 完成。

## 0.1.1 截图兼容性修订

用户在另一台电脑已验证游戏窗口枚举与连接成功，但固定 GDI 返回黑色截图。已将桌面和 CLI 默认改为 FramePool，提供 FramePool / PrintWindow / DXGI / ScreenDC / GDI 显式选择；诊断页更改方式后获取截图会释放旧控制器、重新连接同一游戏窗口，然后采集。实际连接方式写入快照、截图与日志，偏好保存；失败或切换会清除旧预览。通信协议升为 v2，桌面和引擎需要使用同一测试包。

统计 Maa 原始 BGR / BGRA 像素的平均亮度和暗像素比例，近黑画面显示警告并保留真实 PNG。判据为 RGB 三通道均不大于 8 的像素占比至少 99.5%，且平均亮度不大于 2/255；仅用于排查，不能区分截图故障与真实加载过场。DXGI / ScreenDC 获取屏幕上的游戏区域，须保持游戏完整可见且未被遮挡。截图方式能力按固定 [Maa v5.14.3 文档](https://github.com/MaaXYZ/MaaFramework/blob/v5.14.3/docs/en_us/2.4-ControlMethods.md) 与参考项目的截图策略核对。

独立回归共 14 项 Rust、3 项 Edge 界面检查通过。新增真实 Maa 固定图捕获覆盖纯黑、近黑、暗场与蓝色，验证诊断阈值、通道与 PNG 像素保持；前端 IPC 测试覆盖五种方式、切换后先重连再截图、黑帧提示、失败清除旧预览及重连失败后再次尝试。界面测试使用可辨识的模拟响应，不代表游戏截图验证。严格 Clippy、TypeScript 和 Vite 构建通过。新的截图方式尚需用户测试电脑验证实际游戏渲染，不能宣称已完成实机黑屏修复验收。
