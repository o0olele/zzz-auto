# 预备编队按槽位扫描

当前参考实现将管理页改为按游戏列表位置识别，并同步实际名称。体力计划保存的是预备编队下标，不能因改名而漏识别或把其他卡片写到这个下标。依据为参考仓 team_config.py、predefined_team_checker.py、agent_template_matcher.py、predefined_team_recognizer.py、team_select.yml 及测试仓的两张原始预备编队画面。管理页没有 SELECT、TEAM 或预备出战，仍与战前选择页分开。

新日常资源使用 schema 9，固定六个卡片区域，每页前进四槽，最多二十槽。先复位顶部；后续页须与前页末两张可靠卡片一致，翻页未生效或位移不符时拒绝回写。新翻页从 (960,715) 到 (960,150)，明确按下后等待 600ms、逐段移动约 100ms、到终点保持 1000ms 再抬起，之后等待页面稳定；按下节点自动释放，停止仍由输入恢复清单兜底。输入前后延时不能替代按住时长，Maa TouchDown/TouchMove/TouchUp 的依据为随 SDK 保存的任务流水线协议。队名取卡片顶部完整区域中的最大非界面文字，去除空白；缺少名称时保留原名称。人数与三个头像共同证明成员，空队须明确 0/0；头像不明确不能清空旧成员。成员仍按头像位置保留空位。

回执继续携带冻结名称，另加可缺省的实际名称；旧回执只更新成员。按槽位的分页回执和旧版按名称回执分别验证，不能混用。名称可与其他槽位相同，脚本始终由原下标保持；旧版名称匹配在同名时拒绝歧义。配置回写继续核对原配置、账号及修订，合并后一次提交；保存失败只补存，暂停重新扫描。前序编队检查后的体力种子采用同一次已保存扫描，不改换计划下标或脚本。

schema 1 至 8 的节点与扫描方式保持；管理页 schema 9 单独固定五份槽位来源和新翻页节点，协议升级 v50，导入预览因名称转换变化升级 v20。后续[公共战前选择](team-selection-slots.md)在 schema 10 接入实际按钮和反馈，当前参考来源已全部核对；schema 9 的原选择方式保留。全部验证使用离线控制器及既有图片，实机验收保留。

十五项 Rust 专项及相邻共五十二项 Rust、六项界面检查通过，其中新增一项界面用例。原始管理页在全部配置队名不同的情况下读取六张卡片，原始选择页不能生成管理回执；自定义控制器从已打开并复位的管理页开始，组合原始卡片构造五页，核对四次实际投递、按住时长、取消释放、二十槽合并、安全返回和一次回写。组合分页不作为实机翻页证明。当前来源四十条中三十九条接受，余一份选择代码继续拒绝，见[验收记录](../migration/acceptance.md#2026-年-10-月-29-日-m5-预备编队按槽位扫描)。
