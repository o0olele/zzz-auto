# M2 邮件 Pipeline 原型

2026 年 10 月 15 日按用户决定开始 M2，M1 保留待验证项。本批实现完整邮件流程的离线原型、专用资源包和业务检查点；桌面应用列表中的邮件仍为待迁移，当前入口拒绝真实游戏控制器。共享运行槽、桌面输入恢复登记和实机验收是 M2 的后续工作。

## 构建与复跑

在主仓根目录执行，不依赖 Python：

```powershell
cargo run -p od-tools --locked -- mail-bundle --reference ../ZenlessZoneZero-OneDragon
cargo test --manifest-path zzz-od-test/test/zzz_auto/rust/Cargo.toml --target-dir target/validation --locked --test mail_pipeline -- --test-threads=1
```

默认输出为 `resources/generated/mail/`。来源为参考仓 `email.yml`、`menu.yml`、`normal_world_basic.yml` 中十个区域及其模板。OCR 使用 `models.lock.json` 固定的 ppocrv5 检测、识别模型与字典。构建器核对模型原始字节，将旧矩形转换为 Maa ROI，保持 1920×1080，不缩放模板。独立二值掩码的 0 像素转换为 RGB `(0,255,0)`，255 像素保持原值，显式启用 `green_mask`，模板方法为 5。

`resources/mail/pipeline.json` 是手写流程源，构建后才写入生成包的 `pipeline/`，避免默认健康检查包加载未生成的区域引用。构建器将固定 ROI / target 别名展开为数组：Maa 的字符串 ROI / target 是识别结果引用，不能代替区域配置坐标。

`mail-manifest.json` 保存源 YAML、模板、掩码、手写流程和生成文件的 SHA-256，记录 SDK 与坐标基准。相同输入可重复生成；来源与输出不得重叠，全部输入验证后才写入；输出含外来文件或符号链接时拒绝，不删除用户文件。清单保留 `accepted=false`，直至实机验收。

普通 `convert-screen` 仍保留既有 LCS、掩码和颜色转换限制。本包只提供邮件所需区域的精确正则和掩码转换，不代表所有画面或 LCS 已完成等价验收。

## 流程与识别

依据为旧仓 `docs/game/screens/邮件.md`、`大世界.md`、三个 screen_info 和 `EmailApp`。测试复用大世界、菜单、可领取列表、已领取列表和奖励弹窗五张真实截图；自定义控制器在点击后延迟两次截图再换帧，交给真实 Maa Tasker 完成识别、轮询与动作。

完整路径：大世界持有 Alt 点击菜单 → 释放 Alt → 邮件 → 核对标题和全部领取 → 判断按钮状态 → 领取 → 核对奖励弹窗 → 确认 → 核对已领取列表 → 返回菜单 → 返回并核对大世界。也可从菜单或列表进入；未知画面超时，非本次领取产生的通用弹窗不自动接管。

“全部领取”变灰后仍能 OCR 命中。可领取要求列表锚点与 RGB 黄色像素；已领取要求列表锚点与文字区域灰色像素。黄色采用 `[150,140,0]..[255,255,100]`、至少 150 像素；灰色采用 `[80,80,80]..[190,190,190]`、至少 150 像素，文字 ROI `[154,1012,107,32]` 来自已有邮件文档。颜色方法显式为 4（RGB）。不能用组合识别引用的节点级 `inverse` 代替子识别取反。

颜色只在现有两张列表图上验证，主题、亮度、悬停、过场和版本变化仍需实机证据。弹窗要求“获得”标题及“确认 / 确定”按钮；“确定”变体没有真实截图，其画面、位置和后续状态均不记为已验收。

## 暂停与结果

`PipelineControl` 区分请求和执行确认。向其他线程提供的 `PipelineRequest` 只能请求暂停 / 停止，不能清除取消或确认队列静止。继续必须等待执行方确认已暂停，停止优先且不能被继续覆盖。`MailRun` 保存运行 ID、阶段、领取尝试、已见奖励、返回阶段和有效耗时。

`execute()` 运行到完成、失败、超时、暂停或停止。每段沿用 M1 的停止与清理：等待 Tasker 静止、显式释放 Alt 和鼠标通道、等待 inactive；释放失败保留失败与待清理责任。请求本身不能被显示为已经暂停或停止。

暂停后调用 `resume()` 再 `execute()`。ID、领取检查点和有效耗时保留，暂停时间不消耗超时；继续时强制重新截图：奖励弹窗继续确认，已领取列表继续返回，返回途中的菜单或大世界接续收尾。终态禁止直接重跑，下一轮使用新 ID。暂停期间请求停止后，调用 `execute()` 确认收尾，不能用继续清除停止。

领取检查点在投递前设置；只有明确没有 task ID 才清除。投递后即使没有成功节点也可能已生效，继续时不再次领取；若仍显示可领取，等待领取后状态直至超时，并报告不确定结果。检查点目前在进程内保留，可以序列化查看，没有跨进程自动恢复入口。成功必须到达每段声明的业务节点，SDK Succeeded 不能单独证明整个应用完成。

`NativeSession::pipeline_events(capacity)` 提供有界展示队列，仅保留任务、Pipeline 节点与动作的消息名、任务 ID 和节点名。回调用 `try_send`，不等待 Tasker、不取得业务锁、不输出原始详情、OCR、图片或 focus；满队列计入 `dropped()`。业务检查点和终态在原生收尾后读取 SDK 保存的任务详情，独立于可丢弃的展示事件。旧 M1 诊断不额外读取节点详情。

任务事件和节点事件分别注册 Tasker sink 与 context sink，共用同一个有界队列。生成的业务节点显式设置非 null 的空 `focus`，使固定 SDK 发送节点进度，不开启全局调试。会话结束时先注销 context 和任务订阅，再清理其余回调和 Tasker，保证原生回调不引用已释放的闭包。

`Node.PipelineNode` 表示流程轮次进度，不能据此猜测某个动作已经完成。动作展示使用 `Node.Action`，回归明确检查 `Mail.ClickClaim` 的 `Node.Action.Succeeded`；业务完成仍读取 SDK 保存的节点结果。会话销毁后两个事件接收端都必须断开，不能有闭包继续持有发送端。

## 验证与后续

测试在独立测试仓，覆盖资源重建、哈希、坐标、掩码与字典、来源保护、五种画面、完整多帧推进、满事件队列、重复执行、领取 / 确认中暂停、领取效果不确定、停止、超时及动作 / 释放失败。设置 `ZZZ_M2_MAIL_REPORT` 为新的 JSON 文件路径可以保存原生观察；未设置时不会改写验收档案。

下一批接入共享运行槽与桌面恢复监督，补暂停 / 继续命令、事件序号和快照、资源包加载与校验，再做真实邮件与异常输入验收。暂停任务必须继续占用运行槽。本批未改桌面协议、应用可用标记或便携包，M2 保持进行中。

实现以固定 SDK 5.14.3 随包文档为准，公开参考为 [Pipeline 协议](https://maafw.com/docs/3.1-PipelineProtocol.html)与[回调协议](https://maafw.com/en/docs/2.3-CallbackProtocol/)。
